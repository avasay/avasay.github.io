The 1979 Pitch: Convincing Bjarne Stroustrup of C++'s Future

Alejandrio VasayDecember 14, 2025

If you could time-travel to 1979 and met with Bjarne Stroustrup, what would you tell him (Updated)

"If you time-traveled to 1979 and found yourself sitting across from me in my office at Bell Labs—just as I was drafting the initial designs for what would become 'C with Classes'—what would you tell me?": This was a homework given by Bjarne Stroustrup when he was my professor at Texas A&M University in Spring Semester of 2013. The course, Generic Programming in C++, was one of the most fun classes I took at Texas A&M University. Take note that I update this essay every so often to reflect a newer C++ release.

From the moment I met the young Bjarne Stroustrup, I knew that he was not someone to be persuaded easily. I just saw a glimpse of the early design of what would become the de-facto programming language of the IT world. I thought to myself that trying to convince Bjarne that the "C with Classes" blueprint would need radical redesign seemed a greater challenge than convincing him I came from the future. Because how do you make someone in the past comprehend the problems that have become existential threats in the future? That is, unless you have seen the future, or someone with a time machine paid you a visit.

At the sight of my iPhone, Bjarne seems finally convinced of my time-travel story and decides to listen. I tell him the future will be a world of exponentially large software, and that his language, which I recommend he rename " C++," must evolve not just to handle complexity, but to shield the programmer from accidental errors.

I show him my list of core design problems from the future, followed by my proposed solutions.

1. The Ubiquitous Pointer Problem (Solution: RAII and Smart Pointers)

The Problem: In 1979, the C paradigm of manual memory management is necessary. But in the future, the sheer size and complexity of applications will turn the manual handling of pointers into the number one source of bugs, security vulnerabilities, and lost productivity. The responsibility of matching every allocation with a deallocation in complex code paths—especially when dealing with exception handling—is simply unmanageable by humans. The ownership model of a resource becomes perpetually ambiguous.

The Pitch: C++ must implement a system where Resource Acquisition Is Initialization (RAII) is the standard. I explain that resources—memory, file handles, network connections—should be tied to the lifetime of objects allocated on the stack. When the object goes out of scope, the destructor handles the cleanup automatically.

To make this practical, the language must provide Smart Pointers (std::unique_ptr and std::shared_ptr). They are classes that use RAII to encapsulate raw pointers, guaranteeing that the memory is released appropriately and enforcing clear ownership. The Smart Pointer is the single most important feature for making C++ reliable and safe for mainstream development.

2. The Unnecessary Copy Problem (Solution: Move Semantics)

The Problem: As C-with-Classes is used for system utilities, graphics, and large I/O, the language will constantly deal with large, resource-owning data structures and buffers. The standard practice in C of passing a large struct to a function often results in the entire structure being copied, which is devastating to performance. When allocating memory for a new data structure, the act of initializing it by copying the contents of a temporary source is an unacceptable overhead. The language needs a concept for cheap, non-destructive resource transfer when the source object is clearly temporary.

The Pitch: We must introduce the concept of rvalue references and Move Semantics (C++11). I explain that when a resource-owning object is about to be destroyed (it’s a temporary or "rvalue"), we don't need to deep copy its data. Instead, we can simply transfer the ownership of its underlying resources (like a buffer pointer or file handle) from the old object to the new one, leaving the old object in a valid but empty state. This is an order-of-magnitude improvement in performance for initializing and manipulating large data structures and is necessary for building efficient libraries.

3. The Replicated Code Problem (Solution: Scalable Generic Programming)

The Problem: C-with-Classes struggles with a fundamental issue: writing reusable code for different types. If a programmer needs a generic list that can store integers, characters, or user-defined objects, the current C solution is dreadful. You are forced to either use the type-unsafe practice of storing everything as a void* (a major source of runtime errors) or use the C Preprocessor (#define) to crudely generate new code for every type, leading to huge code size and painful debugging.

The Pitch: The Blueprint for Templates

To solve this, C++ must introduce a new mechanism that allows us to write the logic for a data structure once, but parametrize it with a placeholder for the type. This system is called Templates. The core is the Class Template, allowing a single definition for a container that provides the efficiency of C with the type safety of a higher-level language.

But the template system will have two critical flaws that must be fixed now:

  1. Rigidity (Variadic Templates): The base template idea will be too rigid; it cannot easily handle functions or classes that require a variable number of arguments (like initializing a future container or tuple). You must design it from day one to include Variadic Templates (C++11).

  2. Developer Experience (Concepts): The biggest flaw is the template error messages. If a programmer misuses a generic component, the compiler will fail to provide a simple error. You must implement Concepts (C++20). This allows the programmer to explicitly state what a type must be able to do (e.g., "This component requires a type that is Sortable"). The compiler can then give a clear, simple error, making generic programming approachable and safe for everyone.

4. The Preprocessor Pitfall (Solution: Compile-Time Safety)

The Problem: The #define preprocessor is a crude text-substitution tool that operates entirely outside the C++ type system, ignoring scope and violating core safety principles. It is a holdover from C and will become an intolerable liability as C++ features grow more complex.

The Pitch: We must prioritize type-safe alternatives. The language needs the ability to execute code and computation at compile time—using type-safe C++—rather than relying on text replacement. Introduce the constexpr (C++11/14/17) keyword. This allows functions and variables to be evaluated by the compiler, eliminating the need for many problematic #define macros and significantly speeding up the final runtime code. The future of metaprogramming is type-safe code, not text-substitution.

5. Embracing Simplicity and Concurrency (The Future Landscape)

Finally, I tell him that C++ needs functional elegance and must be ready for the multi-core world.

  • Simplification (Lambdas andauto ): For smaller, localized functions, programmers should not have to write a separate class or function. Lambdas (C++11) allow the creation of small, anonymous functions in-line where they are needed, dramatically simplifying algorithms and event-handling. Coupled with the auto keyword to reduce repetitive type declarations, the code becomes faster to write and easier to read.

  • The Multi-Core Mandate: The age of single-core CPUs is ending. Concurrency will be everything. C++ must provide high-level, language-integrated tools like std::thread (C++11), and later Coroutines (C++20), to enable safe, portable, and easy-to-manage parallel programming.

"Bjarne," I conclude:

"Implementing these core solutions—especially RAII, Move Semantics, and a robust, well-defined Generic Programming system—will cement C++ as the indispensable systems language for the next fifty years. It will be safe, fast, and feature-rich."

He gives me a tired, yet intrigued, look. “A lot of work for one man,” he mumbles, adjusting his glasses. “But C++… I like it. Very punchy.”
